# QUN Economy — рабочий контур MVP

## Что добавлено

В этой версии QUN Core есть три EVM-контракта:

1. **QUNToken (ERC-20)** — существующий тестовый токен с начальной эмиссией и верхним пределом.
2. **QUNMemberNFT (ERC-721)** — непередаваемый NFT-удостоверение участника. В профиле записаны `projectId`, `roleId` и статус участия. Метаданные NFT доступны через стандартный `tokenURI` и настраиваемый base URI.
3. **QUNPayroll** — предоплачиваемый фонд начислений. Расписание связано с ID участника NFT, а получатель определяется текущим владельцем активного NFT непосредственно в контракте.

Это контракты для локальной EVM-разработки и тестовой сети. Они **не создают собственную независимую блокчейн-сеть** и не являются аудированным финансовым продуктом.

## Как устроено начисление

- Администратор выпускает NFT участника на его QUN-кошелёк.
- В NFT фиксируются короткие идентификаторы проекта и роли.
- Администратор задаёт сумму за период и время первого начисления.
- Казначейство переводит QUN в резерв контракта Payroll.
- Keeper вызывает `payMany(tokenIds)`, когда наступает срок.
- Контракт самостоятельно проверяет расписание, активность NFT и адрес получателя, перечисляет токены и записывает событие `SalaryPaid`.
- Если keeper пропустил несколько периодов, контракт рассчитывает и выплачивает все уже наступившие периоды одной операцией. Повторно получить их нельзя: время следующего платежа и счётчик периодов обновляются в той же транзакции.

**Важно:** контракт не может инициировать транзакцию самостоятельно. Keeper — внешний исполнитель, который оплачивает gas и вызывает контракт. В этом репозитории есть keeper-скрипт с режимом постоянной проверки; для автономной работы на тестовой сети его можно запустить на собственном сервере или через GitHub Actions после настройки секретов. Любой пользователь также может вызвать публичную функцию выплаты, но не может изменить сумму или получателя.

## Ограничения текущей версии

- Один расчётный период — **30 суток**, а не календарный месяц. Это прозрачно заданная MVP-модель; календарные месяцы (с учётом разной длины) следует реализовать отдельным изменением и покрыть тестами.
- NFT непередаваемый. Это защищает привязку роли и начисления к участнику. Для обычных коллекционных NFT нужен отдельный контракт.
- Платёж возможен только при достаточном резерве QUN. Вывести резерв можно лишь после отмены всех активных расписаний; это защищает действующие графики от случайного вывода средств.
- Если NFT отозван, массовая обработка пропускает его; прямой вызов выплаты завершится ошибкой. Администратор должен отменить его расписание, чтобы освободить резерв для последующего возврата.
- У владельца контрактов есть административные полномочия. Для реальной экономики их нужно передать multisig-кошельку и добавить timelock/процедуры управления.
- В этой версии нет аудита безопасности, юридической квалификации начислений, налоговой интеграции или гарантии выплаты фиатной заработной платы. Токены тестовой сети не имеют денежной стоимости.

## Локальный запуск

Требования: Node.js 20 LTS, npm.

```bash
npm install
npm test
npm run compile
```

Ожидаемый результат: тесты QUNToken и QUN Economy проходят, контракты компилируются.

Запуск локальной EVM:

**Терминал 1**
```bash
npm run chain
```

**Терминал 2**
```bash
npm run deploy:ecosystem:local
```

Скрипт выведет адреса QUNToken, QUNMemberNFT и QUNPayroll. При каждом сбросе локальной сети адреса и данные меняются.

## Пример рабочего цикла

После деплоя из терминала Hardhat Console или собственного скрипта:

```js
const projectId = ethers.encodeBytes32String("QUN");
const roleId = ethers.encodeBytes32String("CORE_TEAM");

// Выпустить NFT участнику.
await membership.mintMember(memberWallet, projectId, roleId);

// Настроить выплату 100 QUN за 30-дневный период.
const latestBlock = await ethers.provider.getBlock("latest");
const firstPaymentAt = latestBlock.timestamp + 30 * 24 * 60 * 60;
await payroll.setSchedule(1, ethers.parseEther("100"), firstPaymentAt);

// Пополнить резерв.
await token.approve(await payroll.getAddress(), ethers.parseEther("300"));
await payroll.fund(ethers.parseEther("300"));
```

На локальной сети keeper можно запустить так:

```bash
QUN_PAYROLL_ADDRESS=0x... QUN_PAYROLL_TOKEN_IDS=1,2 npm run keeper:local
```

В PowerShell:

```powershell
$env:QUN_PAYROLL_ADDRESS = "0x..."
$env:QUN_PAYROLL_TOKEN_IDS = "1,2"
npm run keeper:local
```

Keeper проверяет сроки каждые 60 секунд. Для одноразовой проверки установите `QUN_KEEPER_ONCE=1`.

## Тестовая сеть и keeper

В `.env.example` перечислены переменные окружения. Файл `.env` исключён из Git.

Для тестовой сети задайте:
- `QUN_TESTNET_RPC_URL` — RPC выбранной EVM testnet;
- `QUN_TESTNET_CHAIN_ID` — chain ID;
- `QUN_DEPLOYER_PRIVATE_KEY` — временный deployer-кошелёк тестовой сети;
- `QUN_KEEPER_PRIVATE_KEY` — отдельный keeper-кошелёк с небольшим запасом тестового gas-токена;
- `QUN_PAYROLL_ADDRESS` — адрес контракта Payroll;
- `QUN_PAYROLL_TOKEN_IDS` — список NFT ID, разделённый запятыми.

Не используйте ключи основных кошельков. Не коммитьте приватные ключи, seed-фразы или production secrets.

GitHub Actions workflow `.github/workflows/payroll-keeper.yml` запускает проверку по расписанию раз в сутки и вручную. Для этого нужно добавить перечисленные выше параметры в repository secrets. Если секреты не заданы, workflow пропускает платёжный шаг.

1. Проверить контрактный MVP локально и устранить все ошибки тестирования.
2. Добавить интерфейс QUN Economy: создание NFT, расписаний, пополнение резерва и история начислений.
3. Подключить QUN Wallet к чтению on-chain баланса и событий, оставив текущий Supabase-ledger отдельным тестовым модулем до миграции.
4. Добавить индексатор событий и сверку данных с RPC.
5. Выбрать публичную EVM testnet, проверить деплой, keeper и восстановление после остановки.
6. Проектировать календарную зарплату, бюджетирование, роли, проекты, гранты, вестинг, выплаты и управленческие права.
7. Провести threat modelling, независимый аудит и юридическую проверку до использования токена с реальной стоимостью.

## Архитектурное правило

Блокчейн — источник истины для on-chain выпуска, владения токенами и NFT, расписаний и состоявшихся выплат. PostgreSQL/Supabase может хранить профили, черновики, представления истории и индексацию, но не должен подменять on-chain баланс или подтверждение транзакции.
